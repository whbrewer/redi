# REDI: Readiness Engine for Data Integration

REDI turns raw scientific data into AI-ready datasets and writes the output directory that
SetGo consumes. It sits in the middle of a three-tool chain:

```
AIDRIN (assess the raw data)  →  REDI (transform it)  →  SetGo (enrich metadata, FAIR, publish)
 "what is wrong with it?"        "fix it, shard it"        "describe it, make it citable"
```

Each tool has its own skill (`aidrin`, `setgo`). Hand off to them rather than reimplementing
what they do: REDI does not compute fairness/privacy metrics, and it does not own FAIR scoring
or catalog publishing.

## Setup

```bash
source /opt/venvs/drai/bin/activate    # also sets ESMFMKFILE for the climate domain
redi --help
```

If `redi` is not on PATH, the venv is not active. Do not `pip install` into the system Python.

## Commands

| Goal | Command |
|---|---|
| Try it with no data | `redi demo [--domain general\|hpc\|climate\|geospatial\|materials] [-o DIR]`; `redi demo --list` |
| Run the pipeline (default command) | `redi run <input> -o <dir> [-d DOMAIN] [-s STAGES] [-f FORMAT] [--aidrin-report MANIFEST]` |
| Domain-specific readiness assessment | `redi assess <file> [-d DOMAIN] [-o report.json] [--style json]` |
| Propose a pipeline for unknown data | `redi discover <path> [--no-interactive] [-o DIR]` |
| Document an existing workflow | `redi analyze --workflow <Snakefile\|*.nf> [--type snakemake\|nextflow\|bash]` |
| Compare output to ground truth | `redi validate <output_dir> -c config.yaml [--aidrin]` |
| Download then process (climate) | `redi run --download --source esgf\|cds --variable ... -o DIR` |

Useful `run` flags: `-c config.yaml`, `--array` (array data, skips DataFrame steps),
`--normalize minmax|zscore`, `--shards N`, `--verify`, `--provenance` (FlowCept →
`PROVENANCE_CARD.md`), `-v`, `--style rich|simple|json`. `redi run --help` is authoritative;
check it before using a flag you are unsure of.

Pipeline stages: ingest → preprocess → transform → structure → output. Readiness levels:
1 RAW, 2 CLEANED, 3 LABELED, 4 FEATURE_ENGINEERED, 5 FULLY_AI_READY.

## What `redi run` writes

Into the `-o` directory (without `-o`, a hash-named directory under `output/`):

| File | Purpose |
|---|---|
| data files (`.npz`, `.parquet`, `.zarr`, ...) | The AI-ready dataset, usually with train/val/test splits |
| `metadata.json` | Processing record: `input_file`, `domain`, `completed_stages`, `errors`, row/column counts, `columns`, `normalization_stats`, `split`, `saved_files`, run-versioned `provenance`, and `aidrin_assessment` when `--aidrin-report` was used. **This is the REDI↔SetGo contract.** |
| `READINESS_REPORT.md` | REDI's readiness assessment and recommendations for the run |
| `PROVENANCE_CARD.md`, `flowcept_buffer.jsonl` | Only with provenance tracking enabled |

REDI does not write a `DATA_CARD.md`. Data cards are generated by SetGo (`setgo card`).

## Workflow A: starting from an AIDRIN assessment

Use this when the user says AIDRIN has already assessed the dataset. The hand-off is the AIDRIN
assessment manifest, `aidrin_assessment.json` (format `aidrin.assessment/v1`). It records the
file assessed, the column roles, each metric run, and numeric findings.

```bash
redi run <input> -d <domain> -o <dir> --aidrin-report <manifest>
redi run <input> -o <dir> --aidrin-report <manifest> --aidrin-no-apply   # report only
```

`--aidrin-report` checks the manifest describes this input (and warns if the file changed since
the assessment), acts on the findings the **generic DataFrame pipeline** supports, prints what it
cannot do, and records the link and outcomes in `metadata.json` under `aidrin_assessment`. A bad
or unsupported manifest fails before any output is written. It is not supported with `--parallel`.

**What it applies** (each shown as `applied` in the plan):

| AIDRIN input | What REDI does |
|---|---|
| `roles.target` with `confirmed_by_user: true` | Keeps the target out of normalization, encoding and feature selection; label-encodes it if it is text (mapping in `metadata.target_encoding`); writes it as `y` |
| Class imbalance finding **and** a confirmed target | Stratifies the train/val/test split on `y`. Falls back to a random split, and says why in `metadata.split.stratify_note`, if `y` is continuous or has more than 50 values |
| Constant columns finding | Drops numeric columns with a single value. Constant text columns stay |

A target role that is not confirmed is **not** used, because it decides what a model learns to
predict. If `confirmed_by_user` is false, ask the user, then rebuild the manifest with confirmed
roles. Do not just flip the flag in the file without the user's confirmation.

**What it does not apply**, shown as `unsupported` or `advice`:

| AIDRIN finding | What REDI actually does |
|---|---|
| Missing values | Preprocessing drops rows with missing values by default (advice) |
| Whole-row duplicates | Removes fully identical rows by default (advice) |
| Duplicates on specific columns | **Not handled.** Only fully identical rows are removed, so these remain and can leak across train/test |
| Outliers | Clips them (IQR, 1.5x) by default (advice). It does not remove rows |
| Grouping column (`roles.batch`) | **Not handled.** REDI cannot split by group |
| Privacy findings (k-anonymity, HIPAA) | **Not handled.** REDI does not anonymize. Stop and tell the user the data is not safe to publish |

Nothing is applied to domain pipelines (climate, hpc, fusion, ...) or in `--array` mode, and the
plan says so. Settings also need their stage: `-s` that omits `transform`, `structure` or `output`
turns the matching actions off.

**Check the outcomes, not the plan.** After the run, `metadata.aidrin_assessment.applied` lists each
action with `outcome` (`applied` or `not applied`) and `detail`, read from what the pipeline steps
actually wrote. An action can be wired in and still not happen (for example the target column is not
in the data), and REDI prints a warning when that occurs. Report any `not applied` to the user.

1. **Find the manifest.** If AIDRIN only left a markdown report and raw metric JSON, build one with
   `aidrin manifest build --plan <plan.yaml>` (see the `aidrin` skill).
2. **Run with the flag** and read the plan it prints.
3. **Tell the user plainly** which actions were applied, which were not, and why. Do not claim the
   pipeline fixed anything it cannot fix.
4. **Close the loop.** Re-run AIDRIN (via the `aidrin` skill) on the REDI output with the same roles
   and show before/after for the metrics that motivated the pipeline. Report the numbers; do not
   declare the data "ready". That judgment is the user's.
   (`scripts/aidrin/run_aidrin_*.py` are examples of before/after runs.)
5. **Hand off the rest.** List the unsupported items as open issues: work to do by hand (rows
   duplicated on specific columns) or REDI features that do not exist yet (group-aware split,
   anonymization). SetGo preserves the `aidrin_assessment` block but does not use it yet.

## Workflow B: handing REDI output to SetGo

SetGo is the next step: it reads REDI's `metadata.json` and fills the gaps that make a dataset
findable and publishable. Hand off when the user wants FAIR assessment, a data card, a license
or governance check, or publication.

1. **Confirm the output is complete.** `metadata.json` exists, `errors` is empty, and
   `completed_stages` reaches `output`. If `errors` is non-empty or stages are missing, fix the
   REDI run first; SetGo will faithfully score a broken record.
2. **Check the contract:** `setgo schema --validate <dir>/metadata.json`. Only `domain` is
   required, so a pass says little about completeness.
3. **Hand off to the `setgo` skill** and let it drive. Its enrichment loop already knows how to
   pre-populate from a REDI directory (`metadata.json`, `PROVENANCE_CARD.md`,
   `flowcept_buffer.jsonl`) and what to ask the scientist (title, description, license,
   creators, keywords). Do not duplicate those prompts here.
4. **Domain mapping:** SetGo accepts `climate`, `materials`, `life_sciences`, `fusion`, `hpc`,
   `general`. REDI also has `geospatial`, and some REDI cases use domain-specific names (for
   example `xgc1` maps to `fusion`). If the record's `domain` is not in SetGo's list, omit
   `-d` on `setgo assess` and tell the user the domain validators did not run.
5. **Typical sequence:**

   ```bash
   redi run data.csv -d hpc -o ./out --provenance
   setgo schema --validate ./out/metadata.json
   setgo assess ./out --against fair -d hpc --style json
   setgo card ./out
   setgo publish ./out -c croissant      # or huggingface, ckan, observatory
   ```

   Publishing sends data and metadata to an external catalog. Confirm the catalog, repo, and
   license with the user before running `setgo publish`.

## Full chain (AIDRIN → REDI → SetGo)

When the user asks for the whole path, do it in order, one stage at a time, and stop to report
after each. Do not skip ahead if a stage turned up something the user should decide on.

1. AIDRIN assessment exists? If not, use the `aidrin` skill first.
2. Workflow A: translate findings, run REDI, re-assess the output.
3. Workflow B: validate and enrich the record with SetGo, assess, generate the card.
4. Publish only on explicit request.

## Rules

- **Never edit `metadata.json` by hand.** REDI writes it. To change a record afterwards, use SetGo's `Record` (`from_file` → `update` → `save`).
- **Don't convert measurements into verdicts.** AIDRIN scores and SetGo coverage are evidence.
  Report them with their meaning; the user decides whether the data is ready.
- **Check the actual output**, not just the exit code. Read `metadata.json` `errors`, and
  confirm the expected files exist before saying a run succeeded.
- **Large inputs:** do not run big pipelines on a login node. Submit through Slurm (see
  `benchmarks/pipeline/jobs/` for job scripts) or ask the user.
- If a REDI flag or config key is not documented here or in `redi run --help`, read
  `redi/cli.py` or `redi/config.py` before using it.
